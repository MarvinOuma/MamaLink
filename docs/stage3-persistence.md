# Stage 3 persistence

Chanel's original Room work is retained in the branch history. These adapters implement the shared `domain.repository` contracts; presentation code imports `domain.model`, never Room entities. There is one public model/contract family.

## Stored data and representation

Only the agreed fields are stored: caregiver name and optional phone; child name, caregiver and birth date; appointment caregiver, optional child, title, time and optional location. The unapproved email, address, notes, medical notes, gender, description, status and creation-time fields were removed before v2 is released. No clinical or free-form health records are introduced.

Birth dates use ISO-8601 calendar strings via `LocalDate` converters. Appointment instants use UTC epoch milliseconds; sub-millisecond precision is not retained. Optional fields remain SQL NULL. Required names/titles are checked by the repository. Development fixtures contain fictional labels.

## Integrity and writes

A child references an existing caregiver. Appointments reference an existing caregiver and, when childId is supplied, the unique child/caregiver pair. A composite foreign key rejects mismatches on insert and update, and rejects reassigning a child while appointments reference that pair. This holds even for direct DAO writes and concurrent writers.

Profile and appointment inserts use ABORT; explicit updates return affected row counts. A duplicate ID never implicitly deletes a parent or detaches its dependents. Repository inserts require id=0, and updates/deletes return zero for absent IDs.

The conservative deletion policy is RESTRICT: a caregiver with children or appointments cannot be deleted, and a child with appointments cannot be deleted. Delete or explicitly detach the appointments first; then delete children before their caregiver. There is no automatic cascade or implicit unlink. Any future cascade/confirmation flow requires a separate team decision and schema migration.

## Migration and verification

The production factory registers the explicit v1-to-v2 migration. It preserves workspace metadata, creates all three tables and the corresponding indexes, and has no destructive fallback. v1 schema history is unchanged. v2 is regenerated by Room/KSP.

Migration tests create a v1 database from the historical JSON and identity hash, open it using the production factory, compare every table/column/index/foreign key to a fresh generated v2 database, verify metadata, nullable values, relationships, CRUD and reopening, and check that omitting the migration fails without erasing data.

DAO/repository tests cover domain API compatibility, dates/times, nullable fields, row counts, ordering/filtering, active LiveData updates, missing references, mismatched caregivers, reassignment, duplicate IDs and restricted deletion. Existing navigation, workspace and shared-contract tests remain.

CI runs `:app:build :app:lintDebug :app:lintRelease` for debug/release and fails on schema drift. Reports and generated schemas are uploaded for diagnosis. The UI remains the Stage 1 navigation preview; Stage 2/4 will wire profile forms to these contracts. This is not a release-readiness claim.
